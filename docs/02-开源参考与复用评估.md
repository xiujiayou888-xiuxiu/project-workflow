# 02 开源参考与复用评估

## 目标

在需求已确认、正式架构和编码开始前，先判断是否有成熟开源项目、官方模板、SDK、包管理生态、设计系统、部署方案或核心组件可以参考或复用。

目标是避免普通用户重复造轮子，同时避免盲目复制、许可证违规、供应链风险和不合适依赖，并确保任何项目不侵犯第三方权利、不违反适用法律法规或平台/行业规则。这个门禁不扩大项目范围，不自动安装陌生代码，不替用户做付费、授权或高风险决定。

这不是法律意见。涉及受保护内容、个人/敏感数据、跨境或受监管行业、账号权限、商业授权、用户生成内容、模型训练数据或明显高风险用途时，必须暂停自动采用，保留事实证据并进行适当的人工/专业审查。

## 路由规则

| 路由 | 必须动作 | 候选数量上限 | 研究成本 |
| --- | --- | --- | --- |
| R1 轻量 | 快速检查官方模板/常用库；明显一次性脚本可写跳过理由 | 0-2 | 10-20 分钟或同等轻量判断 |
| R2 标准 | 架构/编码前搜索 GitHub、官方模板、包管理生态、成熟核心组件 | 2-5 | 聚焦 V1 核心能力 |
| R3 商业 | R2 + 维护、安全、许可证、部署、升级和二次开发成本复核 | 3-7 | 支持商业交付决策 |
| R4 高风险 | R3 + 安全/合规/数据边界专项复核，必要时先 POC；核查适用法律、行业监管、数据授权和违法滥用风险 | 3-8 | 结论必须可审计 |

不论 R1-R4，合法合规是独立的一票否决项。R1 只能减少研究成本，不能跳过权利和违法风险检查。不要为了显得专业强制 R1 做重型研究。R1 跳过时必须写明：项目足够小、无成熟复用点、成本高于收益，或当前无法联网/无法访问。

## 搜索前先定义能力

禁止按项目名泛搜。先把需求拆成能力清单：

| CAP-ID | 要解决的能力 | 所属 REQ/JOURNEY | 必须自研的理由 | 可复用形态 | 风险等级 |
| --- | --- | --- | --- | --- | --- |
| CAP-001 |  |  |  | 整体项目 / 官方模板 / SDK / 库 / 引擎 / 设计系统 / 部署模板 / 文档参考 |  |

搜索查询围绕能力、技术栈、官方生态和关键约束。例如搜索“Next.js auth starter template official”优于搜索“我要做会员系统项目”。

## 搜索来源

按需选择，不要求全部展开：

- GitHub 仓库、GitHub Topics、Release、Issues、Security advisories。
- 官方模板、官方 SDK、官方示例、框架文档和迁移指南。
- 包管理生态：npm、PyPI、NuGet、Maven、Go crates、Docker images 等。
- 成熟核心组件：认证、支付、文件解析、图像/视频处理、规则引擎、测试、编辑器、图表、搜索、工作流等。
- AI/Agent 项目：模型/平台官方 SDK、Agent 框架、RAG/检索组件、评估工具、提示词/工具调用示例。
- UI 项目：成熟设计系统、组件库、可访问性模式、图标库、图表库和交互引擎。
- 部署项目：平台官方模板、IaC 示例、CI/CD 模板、监控和回滚方案。

不能联网、账号受限、搜索失败或信息查不到时，写 `unknown/未完成`，并说明下一步需要谁用什么工具补查。禁止编造 URL、许可证、维护状态、版本或结论。

## 候选记录

每个候选至少记录：

| 字段 | 内容 |
| --- | --- |
| CAND-ID | `OSS-001` |
| 能力 | 关联 `CAP-*`、`REQ-*`、`JOURNEY-*` |
| 名称与真实 URL | GitHub/官方/包页面真实链接 |
| 仓库/包 | owner/repo、包名、镜像名或官方模板名 |
| 许可证 | SPDX 名称；没有就写 unknown |
| NOTICE/署名 | 是否要求保留版权、NOTICE、修改声明、商标限制 |
| 版本/commit | Release、tag、lockfile version、commit SHA 或 unknown |
| 检查日期 | YYYY-MM-DD |
| 证据 | README、docs、release、issue、安全公告、示例、测试、下载量等 |
| 当前结论 | 进入评估 / 淘汰 / 待补查 |

追加记录：

- `权利与合规边界`：代码/内容/数据/模型/商标/字体/图片/音视频/用户输入的来源、授权范围、地域/行业限制、隐私与留存规则、是否可能被用于违法目的；
- `合规证据`：权利人授权、许可证全文、NOTICE/署名要求、数据处理依据、官方政策或适用规则链接；无法核实写 `unknown/未完成`，禁止猜测“应该没问题”。

Star、fork、下载量只能作为信号，不能作为采用结论。

## 决策类型

最终必须明确选择一种或多种：

- `直接采用`：许可证兼容、维护健康、风险可控、功能匹配；锁定版本并写升级策略。
- `组合组件`：只采用成熟库/SDK/模板片段，项目架构仍自有。
- `Fork 改造`：需要长期维护改动；写清 fork 来源、分支、同步策略和退出方案。
- `只参考架构/交互`：不复制代码；记录参考点和差异化设计。
- `做 POC`：高价值但风险/适配未知；写时间盒、成功阈值和失败停止条件。
- `完全自研`：复用收益小于成本，或许可证/安全/维护/边界不适合。

每个决定都必须说明理由、剩余风险、锁定版本、替换/退出方案和复核人。权利或适法性为 `unknown/未完成` 时，决策不得为“直接采用”或“生产采用”。

## 采用前红线

采用代码、模板或依赖前必须：

- 检查许可证与项目用途、分发方式、商业交付是否兼容。
- 检查版权、NOTICE、署名、商标、专利和修改声明要求。
- 检查代码、内容、数据、模型、字体、图片/音视频和用户输入的权利来源、授权范围及适用法律/行业规则；
- 锁定版本、commit 或包版本，不使用来源不明的浮动代码。
- 记录依赖清单；R3/R4 或高供应链风险项目应记录 SBOM 或等价清单。
- 用隔离环境审查和测试，不自动运行陌生安装脚本或高权限命令。
- 写升级策略、回滚方式和替换路径。

禁止：

- 整库照搬当作自有代码。
- 复制来源不明代码。
- 引入许可证不兼容代码。
- 使用未确认权利来源、授权范围或数据处理依据的资产/数据。
- 实现、部署或推广明显侵犯他人权利、规避监管、欺诈、伤害他人或违法的用途。
- 把停更、高危、无测试或维护状态不明的仓库直接用于生产。
- 因为 Star 多、示例好看或 AI 熟悉就直接采用。

