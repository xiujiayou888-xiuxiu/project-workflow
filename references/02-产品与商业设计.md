# 02 产品与商业设计

## 目标

把已确认需求设计成有完整生命周期、明确价值和现实经营边界的产品。成熟不是功能多，而是用户能获得价值、系统能处理异常、团队能运营、项目能交付。

## 产品设计十层

### 1. 产品立场

- 具体服务哪个细分用户、哪个高价值任务。
- 当前替代是什么，为什么仍被使用。
- 产品承诺什么可测结果，不承诺什么。
- V1 唯一最重要的验证假设。

### 2. 真实角色

按实际区分使用者、购买/决策者、管理员/运营者和受影响者。写清目标、能力、频率、权限、顾虑和成功标准，不虚构画像。

### 3. 完整生命周期

发现/进入 -> 首次使用 -> 激活时刻 -> 核心循环 -> 协作/分享 -> 失败恢复 -> 支持运营 -> 退出/导出/删除。

每阶段写“用户动作 -> 产品反馈 -> 系统/人工后台 -> 成功证据”。

### 4. 核心任务

每项定义触发、入口、前置、最短步骤、输入、选择、反馈、结果、下一步、中断和恢复。先设计一条完整关键路径，不先画页面清单。

### 5. 业务对象与状态

对象的标识、来源、所有者、创建/查看/修改/删除权限、状态转换、重复/并发、撤销、归档、审计、保留、导出、删除和迁移。

### 6. 信息架构与内容

- 导航围绕用户任务，不围绕数据库表。
- 每个页面/命令有一个主要任务、主操作、结果和下一安全动作。
- 术语、按钮、错误和帮助使用用户语言并进入 `项目术语表.md`。
- 空、长、极端、无权限和手机场景仍成立。

### 7. 功能边界

确认项是 `REQ-*`；建议项是 `CAND-*`。V1 按顺序保留：核心价值、安全/数据/恢复、最小运营、证据充分的增强。其余延后。

### 8. 服务与运营

列出前台、API/任务/数据库/第三方、审核/配置/查询/补偿/客服、责任人、响应时间、日志、告警和人工兜底。不能只写“联系客服”。

### 9. 信任与体验

根据项目设计权限、隐私、价格/额度、AI 不确定性、来源/修改/复核、撤销/自动保存/版本、无障碍、弱网和兼容。

### 10. 度量与学习

只设计会改变决定的指标：激活、核心价值、重复使用、质量/信任、成本和商业结果。写清事件、触发位置、数据责任人和使用决定。

## 去通用 AI 产品味

R2+ 在产品文档中写清：

1. 产品立场：对用户任务的明确判断。
2. 主动取舍：为了核心结果舍弃什么。
3. 专属工作流：为什么顺序/反馈/协作只适合本项目。
4. 信任理由：怎样核验、修改、撤销和求助。
5. 工程优势：隐私、成本、速度、离线、审计或迁移中的真实优势。
6. 视觉/交互记忆点：服务任务而非装饰。

换掉名称、Logo 和颜色就能套给十个产品，说明设计未完成。

拒绝：模糊用户、功能汤、无评估/权限/兜底的聊天套壳、万能仪表盘、假数据、数据库直接变导航、只做成功路径。

## 商业可行性

商业/公开产品必须用当前来源研究：

| 维度 | 要回答 |
| --- | --- |
| 痛点与频率 | 是否真的损失时间、钱、机会或信任 |
| 替代与竞品 | 用户现在用什么、价格/限制、为何不切换 |
| 差异价值 | 更快/便宜/安全/准确/省事的具体结果 |
| 第一批用户 | 在哪里找到前 10 个用户/客户 |
| 付费与经济性 | 谁付钱、为什么、价格和毛利逻辑 |
| 实施风险 | 平台、数据、合规、获客、依赖和支持负担 |

结论：

- `Go`：关键用户、痛点、第一用户路径和价值至少有部分证据，无致命风险。
- `Validate First`：有潜力但证据弱；只做一个有期限/阈值的访谈、原型、落地页或试点。
- `No-Go`：无痛点、无优势、无获客、经济性负、关键条件不可得。明确建议不做或改方向。

用户坚持 No-Go 项目，只能记录为有时间/预算上限的学习或实验，不包装为商业机会。

## 全成本与收费交付

创建 `docs/00-成本预算与商业交付方案.md`：

- 一次性：需求、产品、设计、前后端、AI、测试、迁移、部署、文档、培训。
- 工具账号：模型、IDE/设计、托管、证书、开发者账号。
- 运行：服务器、数据库、缓存、对象存储、带宽、邮件短信、监控、备份。
- 按量：模型/API、OCR、地图、支付、搜索、转码等。
- 持续：运维、客服、审核、故障、安全、兼容和升级。
- 风险预留：需求未知、外部审批、数据质量、迁移和返工。

给保守/基准/高使用量三种场景，写日期、来源、假设、预算上限和超限降级。不得承诺一定盈利。

可收费产品还要设计：标准范围与定制边界、定位/不适合人群、安装/开通、演示/验收、版本/套餐/额度、授权/试用/到期、数据/账号归属、支持/SLA、升级、退款/停止服务和资产移交。

## 产物路由

- R1：合并写入 `docs/02-产品框架.md`。
- R2：`02-产品框架.md` + 必要的用户旅程/状态/页面图。
- R3/R4：可拆为 `02-用户旅程与服务蓝图.md`、`02-信息架构与页面地图.md`、`02-业务规则与状态模型.md`、`02-产品度量与运营方案.md`。

只有文档量随风险增加，质量问题不因 R1 而被忽略。

## 产品门禁

- 用户、问题、替代、结果、非目标和 V1 假设清楚。
- 首次价值、核心循环、失败恢复、运营支持和退出已检查。
- 对象、状态、权限和规则能实现与测试。
- 信息架构围绕任务。
- 额外功能仍是 CAND。
- 商业项目有市场证据、成本和交付边界。
- R2+ 至少用原型或薄切片走查关键路径。

失败就回到对应层，不进入全面架构或 UI。
